## Database security

The migration is transactional and creates:

| Object | Guarantees |
| --- | --- |
| `room_invitations` | UUID PK; unique 64-character lowercase SHA-256 hash; FK to Auth user; CHECK fixes `created_by` to existing Owner UUID `4dde6af0-2fd6-4520-86a7-8241acb9c180`; server-created timestamps; at most seven-day lifetime |
| `room_visit_sessions` | UUID PK; unique SHA-256 hash; unique `invitation_id` FK; timestamps; positive lifetime no longer than four hours |
| Expiry indexes | One per table, in addition to PK and unique indexes |
| `room_create_invitation(text, uuid)` | Creates invitation with a server-selected seven-day expiry; returns safe metadata |
| `room_redeem_invitation(text, text)` | Locks invitation, checks state, consumes it and inserts exactly one visit in the same transaction |
| `room_validate_session(text)` | Returns `valid` and expiry only for an active visit; otherwise `valid: false` |
| `room_revoke_session(text)` | Idempotent session revocation |
| `room_revoke_invitation(uuid)` | Revokes only unused invitations; uses the same row lock as redemption |
| `room_list_invitations()` | Latest 100 metadata records with computed unused/used/expired/revoked state; excludes hashes |

Both tables enable and FORCE RLS. There are no client policies. Table grants are revoked from PUBLIC, anon, authenticated, and service_role. Even the owner browser cannot access these tables directly.

All six RPCs are SECURITY DEFINER with an empty `search_path` and fully qualified application tables. EXECUTE is revoked from PUBLIC, anon, and authenticated and granted only to service_role. The function owner is the trusted migration role (normally Supabase `postgres`); it must be able to perform these operations despite FORCE RLS. Existing Diary RLS is untouched. No Guest Pass token becomes a Supabase Auth identity.

Redemption takes `SELECT … FOR UPDATE`, reads `clock_timestamp()` **after** acquiring the lock, checks unused/unrevoked/unexpired state, updates `used_at`, then inserts a visit. An insert error rolls the entire call back, including `used_at`. The unique invitation FK supplies a second independent one-session guarantee. Used state takes precedence over expiry and revocation in responses; reuse never starts another visit.

## Edge Functions and token handling

Six deployed names are prepared: `create-invitation`, `list-invitations`, `revoke-invitation`, `redeem-invitation`, `validate-room-session`, `revoke-room-session`.

Owner endpoints require a Bearer access token, verify it with Supabase Auth `getUser(jwt)`, then compare the verified UUID against the existing owner constant. A decoded claim, frontend owner boolean, or supplied `created_by` cannot authorize them. The owner UUID is also constrained in SQL.

Public guest endpoints require a canonical 43-character base64url token in a JSON POST body. Link-preview GET/HEAD requests cannot redeem. Both token types use Web Crypto `getRandomValues(new Uint8Array(32))` and SHA-256 via `crypto.subtle.digest`. Raw tokens are returned only on successful creation/redemption; SQL receives hashes only. Lists cannot reconstruct invitation links. A session token is not returned if redemption fails.

Requests have a 2 KiB streamed body limit, early format checks, JSON/POST requirements, sanitized errors, no-store responses, no-referrer policy, and explicit canonical-origin CORS. `ROOM_SITE_ORIGIN` supplies the invitation URL origin; request Host/Origin cannot inject it. No raw token, URL, credential, request body, or SDK error is logged by these handlers. CORS is browser containment, not the owner authorization mechanism.

`verify_jwt = false` is explicit for all six endpoints. Public visitors have no Auth JWT, and the frontend uses a publishable API key. Owner routes perform their own Auth-server validation before any database call. This configuration follows Supabase's guidance to authorize in handler code when disabling gateway verification for publishable keys: [API key migration guidance](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys), [Auth integration](https://supabase.com/docs/guides/functions/auth-legacy-jwt).

Only the server adapter reads `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `ROOM_SITE_ORIGIN`. No service credential is added to VITE variables, browser storage, frontend code, public assets, or this repository. The pinned server SDK matches the application's existing Supabase SDK version.

## Frontend flow

1. `/room/invite#<token>` reads the fragment in browser memory. Mounting sends no redemption or invitation-validation request. Only **Enter My Room** redeems; a synchronous in-flight guard prevents duplicate clicks.
2. Storage availability is checked before redemption. Success replaces the history entry to remove the invitation fragment, stores only the Room Session token under `sessionStorage['my-room-visit-v07']`, replaces the route with `/room`, then validates the visit server-side before rendering the room. If storing the visit fails after redemption, the client attempts to revoke it and asks for a new invitation.
3. `/room` and `/my-room` permit existing Owner Auth or a validated visit. Presence of a storage string never unlocks access. The old development bypass is removed.
4. Guest visits revalidate on mounting/refresh, focus, pageshow, visibility return, and every 60 seconds. A timer locks access at the returned expiry. Denial clears the tab token and closes room overlays/controls. Network failure fails closed but retains the token so retry/reload can recover before expiry. Background successful validation preserves room position and overlays.
5. **Leave Room** closes local access and clears sessionStorage immediately, then revokes the hashed session server-side. On failure, the token is retained only in component memory for **Retry ending visit**. The interface explicitly reports that server expiry remains the fallback.
6. Guests retain walking, Tea, Guestbook reading and posting. Diary is visibly locked; no Diary editor mounts or Diary read is sent for a guest. Guestbook remains its existing public/RLS-protected system, including existing owner login/moderation.
7. Owner invitation controls are under a collapsed details panel. Generation presents a link with Copy/Dismiss actions, held only in React memory; Refresh lists metadata only. Only unused invitations offer Revoke.

## Limitations and review decisions

- This is an experience gate. Public geometry/GLB/JavaScript remains public; Guest Pass does not provide DRM or confidentiality for static assets.
- A tab close normally removes sessionStorage, but browser restore/tab duplication can preserve or copy it. A deliberately copied session token can work until server revocation/expiry. The server cannot detect exact tab closure.
- Server revocation is noticed on the next validation (normally at most 60 seconds while visible, or on focus); local expiry is timer-based with server validation as authority. Browser background throttling and client clock skew can affect display timing, never the SQL validity checks. Sensitive data still relies on independent RLS.
- If redemption commits but its response is lost, the invitation remains permanently used and the orphan visit expires within four hours. No retry creates a second visit. Request a new invitation; v0.7 deliberately has no token recovery protocol.
- If Leave Room fails and the page is closed before retry, the copied/original server token can remain valid until expiry. This is disclosed in the UI.
- The invitation list shows the most recent 100; no pagination or expired-row cleanup job is added.
- Public endpoint rate limiting remains a production-hardening follow-up. No CAPTCHA, new accounts, memberships, analytics, or external integrations were added.
- Actual Supabase runtime testing and real multi-backend PostgreSQL concurrency are outstanding review checks, not represented as completed deployment validation.
